§A — Four Theme Boards

One layout, four atmospheres

The same Home composition rendered in all four themes. Identical structure, identical spacing, identical type. Only colour changes — which is the point: themes are a colour system, never a layout system.

§B — Five Dashboards

Five rooms in the same house

All in Midnight Teal. Composition changes per screen — density, ambient layer, radii, which components appear — while the colour contract stays fixed. That difference is what makes each dashboard feel suited to its purpose without becoming a different app.

§C — Theme Comparison

Same components, four themes

The component kit — card, primary button, secondary button, input, chip, selected state, progress bar, orb — held constant while the theme changes. This is how you check that a layout survives a theme swap without special-casing.

§C2 — Primitive Adoption

Why the interface felt unbalanced

Not a palette problem. The shared primitives already existed — adoption was roughly 20%, so about 20 screens hand-rolled their own buttons, empty states and loading skeletons. That is what produced the visual inconsistency: three parallel empty-state implementations and ~100 bespoke CTA buttons.

Real defects fixed, not just restyled.
  • 7 dead navigation targets. Every learning-module CTA called navigate('Tutor'), which is not a registered route — the taps did nothing. They now target the real SULTI tab via navigate('Main', { screen: 'SULTI' }).
  • Invisible loading states in the light theme. Three learning cards hand-rolled skeletons with rgba(255,255,255,0.1) — white on white under Soft Academic Light.
  • White icon on a primary fill. The leaderboard empty-state CTA was 1.88:1; the shared EmptyState derives its ink instead.
  • Dead style properties. Seven style objects spread ...typography.* after literal font values, silently overriding them — editing those literals did nothing.
  • All five atmospheres now render. Home and Community defined an atmosphere but never mounted AuroraBackground, so two of five tabs were flat.
New shared primitives: Skeleton (theme-aware, reduced-motion aware, replaces 20 duplicated style blocks) · SectionHeader · Divider · IconButton (44pt hit target). Adoption of Button itself remains the largest open gap.
§D — Accessibility Audit

Measured contrast, not estimated

Computed with WCAG 2.1 relative luminance. The failing rows are real defects in the current codebase, not hypotheticals.

A1–A3 are the most serious finding in this document. textOnGradient is #FFFFFF in all four themes (src/theme/index.js:31,82,117,187). On the Midnight Teal primary #00D4BD that is a contrast ratio of 1.88:1 — every primary button label in the three dark themes is effectively unreadable. A single onPrimary semantic token fixes all three.
Other defects. getTextStyle scales fontSize by 1.2 but not lineHeight, clipping descenders in large-text mode. getContrastColor branches on the OS colour scheme rather than the active theme, so a user on Obsidian Emerald with the OS in light mode gets light-mode ink on a dark surface. color: '#FFFFFF' on primary also appears at src/theme/index.js:31 while voice/palette.js:23 correctly uses #04111F — two sources of truth disagreeing.
